# 项目设计复盘

如果只看最终输出的一段方案文字，很难判断这个 Agent 是否完成了工作。对运营人员而言，最重要的三个问题是：选中的方案是否在预算和截止时间内，脚本和费用是否属于同一版本，以及方案究竟有没有保存。这个判断决定了项目的设计顺序：先定义完成条件，再决定模型在哪些位置作选择，最后用实际产物和 Trace 检查两者能否对上。

## 1. 成功条件要细到可以反驳一句“已经完成”

“校园毕业季”给了一个容易手算、也容易暴露设计错误的例子。视频报价 12，图文报价 8，预算 10。一次视频估算可以执行成功，同时返回方案不可行；图文候选估算可以返回可行，同时因为缺脚本而不可保存。若只用一个“成功”标志描述这两种情况，模型和调用方都会误判下一步。

因此，工具调用状态、报价可行性和任务完成状态分开表达。候选报价回答“是否值得做”；绑定脚本的估算回答“这个脚本版本能否按此方案执行”；保存事务回答“交付产物是否存在”。在最终预算用例中，第 3 步的图文报价 8 仍然只是候选。第 4 步模型确认并开始制作，第 5 步绑定脚本估算，第 6 步保存，才有可读取的完成方案。这也是为什么即使要减少重复估算，也不能省掉第 5 步。[预算任务 Trace](../examples/review/budget/trace.jsonl) · [保存产物](../examples/review/budget/plan.json)

## 2. 最难的问题不是模型不会写 JSON，而是合法动作可能没有业务进展

早期失败最具有误导性的一点，是模型摘要经常与人的预期一致。它写“视频超预算，评估图文”，但结构化参数仍是视频。另一次它正确选择了便宜的纪念卡，也取得可行报价，之后却继续在两个候选之间切换。前者没有真正改选，后者没有真正采用。用“是否生成了合法 JSON”衡量，两者都可能得到好结果；用“是否基于新观察推动了制作”衡量，两者都失败。

排查时有三个合理的解释，需要分别验证。其一，历史过长使重要观察丢失，于是压缩模型视图并保留原始 Trace。其二，模型可能不能生成目标 ID，于是分别明确指定视频和图文做单步诊断，两种 ID 都成功生成。其三，模型可能不理解要先评估再确认，于是给出异业务示例并冻结四例实测，仍然只有一例通过。各次实验回答的是不同问题；把它们混成一个成功率，对下一步设计没有帮助。[原预算失败记录](../examples/review/history-few-shot/original/verification.json) · [更名场景失败记录](../examples/review/history-few-shot/renamed/verification.json)

最后检查的是动作契约本身。旧实现把所有方案 ID 放进每一轮的评估枚举，即使费用表和任务约束完全没变。只要这个动作一直合法，模型就可以在十步内反复取得同一个答案。最终用已执行工具的事实决定哪些动作仍有意义。有效报价留在上下文里供确认和解释；下一轮仅对未取得有效报价的候选开放评估。对应请求 Schema 和本地校验器读同一份动作集合，避免出现“提示说不能做、执行器却仍允许做”的分歧。这个规则对新方案 ID 和不同费用表同样适用，不需要写死“视频超限自动选图文”。[实现](../src/content_agent/staged.py)

## 3. 把程序安排和模型决策分开，失败才有可解释的含义

选择原生 Python 循环和 SQLite，是为了让一次模型动作、一次工具执行以及一次持久化的关系可以直接查证。程序负责计算费用和时间、补入已有素材引用、检查依赖、提交保存。模型负责选候选、确认采用、根据异常决定下一步或停止。对每次运行，十步上限覆盖两类步骤，格式错误同样消耗余量。这样一次失败既不会被自动重试掩盖，也不会因为后台多做了几个步骤而变成成功。

最终故障用例说明了这个边界。第 4 步生成脚本遭遇一次临时错误，已有素材仍在。第 5 步 Qwen 看见错误后又发出了 `proceed_with_plan`，确认同一个真实报价，程序据此开始第二次脚本调用。后者成功并最终保存，前一次调用始终是失败状态。因此，这条记录能证明“出现错误后，新的模型动作推动了任务恢复”。它不能写成“模型选择了 `retry`”，因为公开动作里没有这个值。[故障恢复 Trace](../examples/review/fault/trace.jsonl)

## 4. 测试设计改变了最终交付的一个数字

验收全部超预算场景时，预算是 6，两个报价是 12 和 8。模型观察后确实选择了 `stop`，程序也没有保存方案。如果测试只断言 `incomplete` 和“无方案文件”，这项验证已经结束。但从运营角度再读一次最终原因，会发现模型说“至少缺 6”，而实际最低缺口是 8 − 6 = 2。这会直接误导追加预算的决定。

修复没有改变模型的停止动作，也没有重写模型原话。程序在完整报价足以判定无可行方案时，单独计算 `minimum_budget_gap` 并生成对外说明，同时把公开摘要保留在 `model_summary`。专门增加的回归测试检查最低缺口来自最低报价；随后只复测这一项。模型在复测中仍误说 6，最终交付数值为 2。这次改进解决的是输出责任边界，不能归功于模型算术能力提高。[首次结果](../examples/review/infeasible-first/output.json) · [定向复测结果](../examples/review/infeasible/output.json)

## 5. 这一版能支持哪些结论

最终真实运行覆盖正常保存、超预算后改选、一次脚本故障后恢复，以及无可行方案时主动停止。另有确定性验证说明：缺信息不会启动模型，重复提交不会增加费用或产物，过期或依赖不匹配的方案不能保存，达到步数上限会明确结束。这些结果足以让评审逐条检查项目要求，但每种真实场景的样本有限，不能据此推断换目录、换模型后的成功率。[验收表](03-evaluation.md) · [重放与缺字段结果](../examples/review/prior-checks/results.json)

后续最值得验证的是**多个可行方案之间的选择质量**。可以固定现有实现，准备三个以上候选，让两个替代方案都满足预算，但分别在费用和耗时上占优，并在输入中写明运营偏好。分别记录模型有没有理解偏好、有没有确认对应的真实报价、最后保存的是否仍是同一方案。另一个边界是临近截止时间：候选估算时可行，确认或保存时已经不可行，系统需要保留已有工作并清楚说明时间缺口。这两类实验比继续给同一预算样例添加提示更能检验设计的适用范围。跨进程失败续跑、并发执行和真实投放均留在本版范围之外。
