# 工程复盘

这个项目最难的地方，是让运营人员能信任“方案已改选并保存”这句话。预算为 10、视频报价为 12 时，模型可以在摘要里写“改用图文”，却在同一条响应的 `option_id` 中继续填视频。此时工具实际执行的是视频估算。反过来，取得图文报价 8 也只说明有可行候选，尚缺模型确认、脚本、绑定估算和保存产物。这两种失败在早期实验中都出现过。[历史原预算用例](../examples/review/history-few-shot/original/verification.json)、[历史更名用例](../examples/review/history-few-shot/renamed/verification.json)

## 1. 如何缩小问题范围

**先检查模型究竟看到了什么。** 早期 Trace 可以看见工具调用失败，却不足以还原部分轮次的原始模型动作。后续记录区分了模型请求、公开响应、解析结果、工具返回和程序安排，并用请求正文核对上一轮的工具观察。这样才能区分“没有传入超预算结果”“模型收到了结果但选错参数”和“选择正确、执行失败”。无法从旧记录还原的动作保持未知。

**再检查上下文长度与参数生成。** 完整工具历史会随重复估算增长，因此尝试过保留磁盘原始历史、压缩发给模型的视图。在有界上下文的固定六例中，最大输入为 4624 token，8192 窗口至少余下 3568 token，仍只有正常链路通过。随后进行四次单步诊断。明确指定视频或图文时，模型都能输出相应 ID；自主选择的两次都返回视频，交换枚举顺序后公开响应也相同。这两组观察削弱了“只要扩窗口”或“图文 ID 无法生成”的解释。样本量不足以判定解码器有缺陷，也不足以排除其他任务中的顺序影响。这些是交付前的诊断，与最终真实任务分开计数。

**把失败标准定在运行前。** 阶段动作拆成评估候选和确认采用后，曾加入两段使用不同名称、金额和 ID 的合成示例，并冻结四个用例。原预算用例中模型反复选择视频。更名用例中模型确实从报价 19 的访谈切换到报价 11 的纪念卡，但一直没有确认采用。全部超预算用例耗尽步数；只有首选本身可行的用例完成保存。这个结果说明，仅看摘要、只看一次可行报价或只统计程序正常退出，都会高估效果。项目按预定条件停止叠加示例。[冻结条件](../examples/review/history-few-shot/frozen.json)、[四例历史证据](../examples/review/history-few-shot/)

## 2. 最终修复为何落在业务规则上

相同任务的预算和截止时间由输入指纹固定。对同一方案、同一费用表版本，成功取得了候选报价后，再调用相同候选估算没有新增成本信息。旧实现仍把所有方案 ID 放在每轮允许的评估集合中，所以即使模型重复选择，校验器也会放行。

最终实现从该任务已经成功执行的工具结果生成当前动作集合。未报价方案可以评估；已报价且在当前时刻仍可行的方案可以用真实 `estimate_id` 确认；模型始终可以停止。发给模型的 Schema 和执行前的本地校验共用同一规则。即使只剩一个未报价候选，程序也要等模型实际选择。这样既避免重复调用，也保留模型提前停止或选择替代方案的可能性。[阶段实现](../src/content_agent/staged.py)

这里有一个容易误删的步骤。**生成脚本后的绑定估算必须保留**，因为它核对的是当前脚本版本、素材依赖和可保存性。旧候选报价可以帮助模型选择方案，却不能证明一个后来生成的脚本可保存。保存入口还要按当前时间复核截止时间，并在事务提交成功后才标记任务完成。[业务工具](../src/content_agent/tools.py)、[状态存储](../src/content_agent/state.py)

## 3. 用实际结果检查修改

| 情境 | 关键观察和后续动作 | 可确认的结论 |
|---|---|---|
| 超预算改选 | 视频费用 12、预算缺口 2 → 模型实际选择图文 → 报价 8 → 模型明确确认 → 第 6 步保存 | 这次完整路径成功；模型选择和程序制作分别可追溯。[验证](../examples/review/budget/verification.json) |
| 临时脚本错误 | 第 4 步生成脚本失败 → 模型第 5 步再次确认原报价 → 程序发起新脚本调用 → 第 7 步保存 | 首次失败仍为失败，已有素材保留。这次恢复来自新的模型动作，动作字面值是 `proceed_with_plan`。[Trace](../examples/review/fault/trace.jsonl) |
| 没有可行候选 | 视频 12、图文 8、预算 6 → 模型主动停止，但把视频缺口 6 说成最低缺口 | 停止动作正确，解释中的数值错误。最低缺口应按最低报价计算，即 8 − 6 = 2。[首次输出](../examples/review/infeasible-first/output.json) |

最后一项暴露了另一个工程问题。程序已经有正确的逐方案费用，最终用户看到的原因却直接复制了模型摘要。修复后，程序根据费用表生成说明及 `minimum_budget_gap`，原话单列为 `model_summary`。增加回归测试后仅对该项复测一次，模型仍说 6，程序输出正确的 2。改善的是交付给用户的数值准确性，模型自身的算术表述仍有局限。[定向复测输出](../examples/review/infeasible/output.json)、[最终回归记录](../examples/review/tests.txt)

## 4. 技术取舍和后续重点

Python 原生循环加 SQLite 已能展示模型选择、工具执行、异常回交、原子保存和幂等重放。对这道题，最有价值的工程投入是让每项结论能落到一条真实动作和一个可核对产物。十步上限同时约束模型纠错和程序安排，能够暴露停滞。相应代价是模型提前停止时任务会真实未完成，程序不能兜底替它选方案。

目前只验证了本地 Qwen、合成目录、模板脚本和串行耗时的有限用例。若继续做实验，第一优先级是固定现有实现，在**三个以上候选且有多个可行替代**的目录中分别统计“选出替代”“确认真实报价”“实际保存”三项，再增加临近截止时间的任务，检查确认前可行而保存时已超时的情况。跨进程失败续跑属于加分项，本版保留已有状态与失败证据，但没有实现恢复执行。

以上是根据代码与运行记录能复核的工程经验。候选人的实际投入、亲手验证过程及个人学习体会，仍由候选人根据自身经历补充。[个人填写项](04-ai-usage.md)
