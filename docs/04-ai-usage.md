# AI 辅助设计、实现与验证记录

我把项目定义为一个给内容运营人员使用的规划工具。运营输入活动主题、预算和截止时间，最终需要拿到一份能执行、能算清费用、能找到保存位置的活动方案。围绕这个目标，我确定了“校园毕业季”的业务场景、四个工具、Python CLI 的交付形式，以及缺信息、超预算、工具失败和重复执行时的验收要求。我用 Codex 讨论设计、检查已有实现、修改代码并执行测试；本地 Qwen 则是被评估的运行时决策模型。下面按几个实际改变过实现的设计问题记录这次协作。

## 一、把业务约定变成可检查的状态

| 我的设计约定 | AI 协助细化的实现办法 | 判断设计是否成立的方法 |
|---|---|---|
| 预算是活动的预计执行费用，估算操作免费。活动耗时先按串行计算。 | 每个候选分别保存费用明细和耗时。预算 10 时，先估视频 12，再估图文 8，最终采用图文就只报 8。保存时用当前时间重新核对剩余时间。 | 比对目录明细、绑定估算和保存产物。用固定时钟测试刚好能完成及保存前已超时两种情况。 |
| 缺预算或截止时间时，运营需要知道该补什么。相同任务重复提交不能多保存一份。 | 在模型调用前做必填校验；对规范化业务输入计算指纹。SQLite 用任务记录和方案记录分别保存执行状态与交付产物。 | 缺字段时检查 `missing_fields` 和零工具调用；重放前后比较方案数、引用及费用；同 ID 改预算须报冲突。 |
| 工具失败后要保留之前的工作，不能把失败写成成功。 | 每次工具调用分配独立调用 ID。失败、部分成功和成功分别记录。临时故障只绑定当前任务的首次脚本调用，后续决定交回模型。 | 在 Trace 中找到第一次脚本的错误、下一轮模型的公开选择及第二次脚本调用，分别核对两个步骤的状态。 |

这部分设计给模型设定了清楚的业务边界。预算是否超限由费用表计算，能否保存由依赖和时间检查决定；即使模型在摘要中宣布“完成”，也只有实际保存事务成功才能返回 `completed`。[业务工具](../src/content_agent/tools.py) · [任务状态与保存](../src/content_agent/state.py) · [输入与重放实测](../examples/review/prior-checks/results.json)

## 二、从通用工具循环改成分阶段决策

最初的原生循环让 Qwen 每轮从四个工具中选择一个，并填写全部参数。我要求用真实运行回答一个问题：模型有没有利用上一次工具结果？Codex 协助检查下一轮实际发送的请求，并把模型公开动作、校验错误、程序补全的参数和真实工具结果分别记入 Trace。这一步让我们能区分三件事：模型收到过什么、模型实际选了什么、程序最后执行了什么。

看到模型能取得报价却反复估算后，我提出沿用题目允许的预设流程，把常规制作和业务选择分开。讨论中形成了两个具体动作：`evaluate_option` 只评估指定候选；`proceed_with_plan` 必须由模型明确给出方案 ID 和真实估算 ID，才表示采用。Codex 将这一区别落实到阶段 Schema、本地校验和状态转换中。模型确认后，程序才用已有素材生成脚本、绑定脚本重新估算，再校验并保存。出错或部分成功时重新进入模型决策点。这个设计保留了改选、确认和停止的真实选择，同时减少了模型抄写内部产物 ID 的次数。[阶段实现](../src/content_agent/staged.py) · [执行循环](../src/content_agent/agent.py)

## 三、AI 参与过哪些改进，实验又否定了什么

围绕重复估算，我先要求控制变量：固定原 Qwen、业务输入和步数，只压缩模型看到的历史，磁盘保留完整记录。Codex 实现了带来源的最近报价、缺失依赖和重复次数摘要。后续又做了四次单步诊断。明确指定图文时，模型能正确生成图文 ID；自主选择时，仅交换枚举顺序没有改变那一次输出。因此，没有依据去改解析器，把摘要里写的“图文”强行覆盖到动作参数上。

随后，我限定 AI 只增加两段不同业务的合成示例，并预先固定四个用例。Codex 编写示例并执行批次。首选可行场景保存成功，原预算场景、更名替代场景和全部超预算场景均未达标。尤其是更名场景，模型已经看见替代报价 11 满足预算 14，却没有确认采用。这个失败把问题缩小到**取得有效报价以后，程序仍允许模型反复评估同一候选**。按预定停止条件，示例提示实验到此结束。[冻结条件和四例记录](../examples/review/history-few-shot/)

收尾时，我要求从实际工具结果构造可选动作，并用同一规则做执行前校验。Codex 将规则实现为 `available_branches`：同一任务、同一目录版本已有成功候选报价，就复用该结果；未报价候选可以评估；当前时间下仍可行的报价可以确认；模型始终可以停止。确认分支把方案 ID 与对应估算 ID 配对。即使只剩一个替代候选，也要等 Qwen 真正选择它。脚本生成后的绑定估算仍执行，因为只有这次估算才能核对当前脚本版本和保存依赖。[动作集合与校验](../src/content_agent/staged.py) · [针对这一改动的测试](../tests/test_staged.py)

## 四、代码完成后怎样验证

Codex 在共享工作区执行了离线 CLI、自动测试和真实 Ollama 任务。离线 Mock 使用固定规则，只用于验证流程。自动测试负责验证计算和状态边界；真实模型任务负责检验模型是否真的观察、改选、确认或停止。三类结果分别保存。

- **回归测试。** 覆盖重复评估被拒绝且仍消耗步数、错误估算 ID 无法进入制作、当前时间变化后报价不可确认、失败步骤保留，以及程序制作阶段同样受上限约束。修复最终缺口说明后，最终提交的 59 项测试全部通过。[测试记录](../examples/review/tests.txt)
- **真实模型。** 最终首批四例各运行一次。预算场景中，Qwen 看见视频报价 12 超过预算 10，实际选择图文，取得报价 8 后明确确认，程序随后保存。故障场景中，模型在脚本错误后再次确认已有报价，产生独立的第二次脚本调用并恢复保存。[预算路径](../examples/review/budget/trace.jsonl) · [故障路径](../examples/review/fault/trace.jsonl)
- **针对缺陷复测。** 全部超预算时，模型主动停止，却把最低缺口 2 说成 6。程序改为用工具费用计算最终说明，同时保留模型原文。只复测受影响的一项，因此交付阶段合计五次真实任务运行。原失败说明和定向复测都有记录。[首次输出](../examples/review/infeasible-first/output.json) · [修复后输出](../examples/review/infeasible/output.json)
